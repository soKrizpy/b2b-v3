# Security Notes — Bits2Bytes

## Supabase Free plan: leaked-password protection

**Status:** Accepted platform limitation; not enabled.

The Supabase Auth leaked-password protection feature is reported as disabled by the Security Advisor. The current Bits2Bytes project uses the Supabase Free plan, so this hosted Auth control is not available in the current plan. Do not represent this finding as fixed, and do not add a paid-plan dependency solely to clear the warning.

## Authentication and Edge Functions review

The live project currently has two active Edge Functions:

- `student-mpin-login`: `verify_jwt=false` is intentional because students authenticate with WhatsApp + six-digit MPIN rather than an existing JWT. The function validates request method and input shape, calls the private verification RPC using a server-side secret, then issues a Supabase Auth session only after successful verification.
- `admin-list-users`: `verify_jwt=false` is paired with explicit in-function Bearer-token validation using `auth.getUser(token)`, followed by a database lookup requiring `profiles.role = 'admin'` before any account listing. Do not remove either check or rely on client-side role state.

### Student MPIN controls verified

- MPIN values are bcrypt hashes (cost 12), not plaintext.
- `private.verify_student_mpin` is SECURITY DEFINER with a fixed search_path and is executable only by `service_role`.
- The public RPC wrapper is SECURITY INVOKER and is also executable only by `service_role`; anon and authenticated execution checks return false.
- The private attempt table is inaccessible directly to anon/authenticated/service_role clients; the function owner accesses it internally.
- Only failed credential checks are counted per normalized phone number. Five failures within a 15-minute window trigger a 15-minute lockout; a successful verification clears that phone's counter. Per-phone advisory transaction locking serializes concurrent checks so parallel requests cannot race the counter. This correction is in `supabase/migrations/20261122104947_count_only_failed_student_mpin_attempts.sql`.

**Residual operational risk:** Because lockout is keyed to the phone number, someone who knows a student's number can intentionally trigger five failed attempts and temporarily deny that student login. This is an availability/abuse tradeoff in the current anti-brute-force design. Monitor support reports and consider adding trusted edge-level/IP-based throttling or CAPTCHA only after verifying the hosting headers and UX; do not weaken the MPIN attempt limit.

## Storage review

Live database inspection found **zero Storage buckets and zero Storage RLS policies**. There is no current user-upload bucket surface to harden. If uploads are introduced later, create private buckets by default and add explicit per-role/object ownership policies before enabling client uploads.

## Database access baseline

- All 31 tables in the exposed `public` schema have RLS enabled.
- Anonymous table privileges have been revoked broadly; only explicitly public read-only catalog/announcement access is granted.
- Service-only verification data remains in the unexposed `private` schema.
- Default privileges for objects created by `postgres` are now hardened: future public tables, sequences, and functions receive no automatic grants to `anon`, `authenticated`, or `service_role`, and future functions created by `postgres` do not receive default `PUBLIC EXECUTE`. This is recorded in `supabase/migrations/20261122104836_harden_postgres_default_privileges.sql`.
- Supabase reserves the `supabase_admin` default privileges; PostgreSQL correctly rejects attempts to alter them. Objects created by `supabase_admin` may still inherit its grants. A live ownership check currently finds **no public tables, sequences, or functions owned by `supabase_admin`**; installed extensions are in `extensions`, `vault`, and `pg_catalog`, not `public`. Do not attempt to bypass Supabase's protected role membership. Re-check object ownership after platform/extension changes. See [Supabase's explanation of protected default privileges](https://supabase.com/kb/troubleshooting/cant-change-the-default-privileges-of-supabase_admin-in-the-public-schema-448af9).

## Compensating controls and operating rules

1. Keep staff accounts limited to trusted, individually assigned identities. Never share one staff login between people.
2. When provisioning or rotating a staff password outside the app, use a unique password of at least 12 characters generated by a password manager; do not reuse passwords from other services.
3. Do not add public sign-up or client-side password provisioning without a reviewed server-side account lifecycle and password policy.
4. Preserve student MPIN bcrypt hashing and server-side attempt throttling. Do not expose the private attempt table or verification function to anon/authenticated roles.
5. Keep RLS and role checks in the database/Edge Functions. UI checks are not authorization controls.
6. Re-run Supabase Security Advisor after database/auth changes. The leaked-password warning is expected to remain until the project plan supports the hosted feature or the plan changes.

## Explicit residual risk

Because the hosted leaked-password check is unavailable on the current plan, Supabase Auth does not automatically reject passwords found in known breach datasets. The manual password-manager rule above reduces risk but is not an equivalent Have I Been Pwned check. Track this as an accepted limitation, not a completed remediation.
